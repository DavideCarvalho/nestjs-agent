The default `TokenStreamSink` (`InProcessTokenStreamSink`) buffers a run's tokens in the process
that started it — reconnect from a different pod and there's nothing to replay. `-transport-redis`
implements the same `TokenStreamSink` SPI over Redis, so any replica can `subscribe` to any run's
stream.

## Minimal example

```ts
import { RedisTokenStreamSink } from '@dudousxd/nestjs-agent-transport-redis';
import { AgentModule, HeaderActorResolver } from '@dudousxd/nestjs-agent';

@Module({
  imports: [
    AgentModule.forRoot({
      model: myModelProvider,
      actorResolver: new HeaderActorResolver(),
      // myRedisClient: a RedisStreamClient (see below); options: { keyPrefix?: string; ttlSeconds?: number }
      sink: new RedisTokenStreamSink(myRedisClient), // shared across every replica
    }),
  ],
})
export class AppModule {}
```

## `RedisStreamClient` — bring your own driver

The package takes zero dependency on `ioredis` or `node-redis` — it depends on a small interface,
`RedisStreamClient`, that your app implements over whichever client it already runs:

```ts
interface RedisStreamClient {
  rpush(key: string, value: string): Promise<void>;
  lrange(key: string, start: number, stop: number): Promise<string[]>;
  set(key: string, value: string): Promise<void>;
  get(key: string): Promise<string | null>;
  publish(channel: string, message: string): Promise<void>;
  subscribe(channel: string, onMessage: (message: string) => void): Promise<() => Promise<void>>;
  del(...keys: string[]): Promise<void>;
  expire(key: string, seconds: number): Promise<void>;
}
```

A run's `:chunks` and `:state` keys expire `ttlSeconds` (default `3600`) after the run's last write;
the TTL slides with each write and is set on both keys when the run ends or fails. `ttlSeconds: 0`
keeps them until `close()`. An adapter without `expire` still streams, but its keys never expire.

A subscribed Redis connection can't run other commands, so most drivers need a **dedicated**
connection for `subscribe` — the sink only calls it from `subscribe()`:

```ts
// adapting ioredis: one command connection, one subscriber connection
import Redis from 'ioredis';
import type { RedisStreamClient } from '@dudousxd/nestjs-agent-transport-redis';

function ioredisStreamClient(redis: Redis, sub: Redis): RedisStreamClient {
  return {
    rpush: async (key, value) => { await redis.rpush(key, value); },
    lrange: (key, start, stop) => redis.lrange(key, start, stop),
    set: async (key, value) => { await redis.set(key, value); },
    get: (key) => redis.get(key),
    publish: async (channel, message) => { await redis.publish(channel, message); },
    subscribe: async (channel, onMessage) => {
      const listener = (ch: string, message: string) => { if (ch === channel) onMessage(message); };
      sub.on('message', listener);
      await sub.subscribe(channel);
      return async () => {
        sub.off('message', listener);
        await sub.unsubscribe(channel);
      };
    },
    del: async (...keys) => { await redis.del(...keys); },
    expire: async (key, seconds) => { await redis.expire(key, seconds); },
  };
}
```

<Callout type="info" title="No driver dependency, on purpose">
Requiring your app to adopt a specific Redis client just to stream tokens would be the wrong trade.
`RedisStreamClient` is the seam: implement its eight methods over whichever client (`ioredis`,
`node-redis`, a cluster client) your app already runs, and `RedisTokenStreamSink` never needs to
know which one.
</Callout>

## How it's keyed

Per run (`keyPrefix` defaults to `agent:stream`):

| Structure | Key | Purpose |
|---|---|---|
| LIST | `<prefix>:<runId>:chunks` | Every chunk (base64) appended in order — what a late subscriber replays before following live. |
| pub/sub channel | `<prefix>:<runId>` | A wake-up published after each append, on end and on `close()`, for subscribers already caught up. |
| terminal marker | `<prefix>:<runId>:state` | `{ t: 'end' }` or `{ t: 'fail', error }`, set when the run ends — a reconnect after completion sees the ending instead of hanging on an empty subscribe. |

Both keys expire `ttlSeconds` after the run's last write (see above); `close(runId)` deletes them
at once.

## What a token costs

Consecutive `text` frames are gathered while the previous send is still on the wire and go out as
one `text` chunk: one `RPUSH`, then the `PUBLISH` wake with the TTL re-arm alongside it. No timer is
involved, so a model streaming faster than a Redis round trip costs one send per burst, and a slow
stream still goes out a token at a time with no added latency. The `PUBLISH` waits for the `RPUSH`,
so a woken subscriber always finds the chunk it was woken for. Non-text frames keep their place
between the gathered text around them. Writers opened for the same run in one process share what
they gather, so a delegated run's text and its parent's next frame keep the order they were written
in, and `flush()` writes whatever is gathered without ending the stream.

A gathered send that fails is raised by the writer's next `write`, `flush`, `end` or `fail`, not by
the `write` that gathered it.

A subscriber reads the list with `LRANGE` from its cursor on every wake, and reads the terminal
marker only when it attaches and once an `end` wake arrives; after seeing the ending it reads the
list once more, so chunks appended just before the marker are not lost. Every subscriber reads the
same stored list, so SSE frame ids and `?after=` cursors are the same on every replica.

A subscription passed `{ signal }` (the chat routes pass one that aborts when the client
disconnects) unsubscribes from the channel as soon as it aborts, even on a run that never writes
again.

A subscriber also stops, as if the run had ended, once the run is gone: `close()` deleted its keys,
or `ttlSeconds` passed with nothing written — by then the keys have expired, whether the run crashed,
is parked past its TTL, or never started. A run that writes again before a full TTL passes is still
followed, and a subscriber whose wake-up was lost picks the chunks up from the list instead of
ending. Under `ttlSeconds: 0` only `close()` ends a silent run's subscribers.

A run that ended in failure re-raises as `AgentStreamError` (from `@dudousxd/nestjs-agent-core`) on
the subscriber side rather than silently closing, so a reconnecting client can tell "the run is done"
from "the run failed" the same way it would against the in-process sink.

## Exports

| Export | Kind | Purpose |
|---|---|---|
| `RedisTokenStreamSink` | class (`TokenStreamSink`) | `new RedisTokenStreamSink(client, options?)`; `open` / `subscribe(runId, { signal }?)` / `close`, backed by the LIST + pub/sub + marker scheme above |
| `RedisTokenStreamSinkOptions` | type | `{ keyPrefix?: string; ttlSeconds?: number }` — defaults `agent:stream` and `3600` |
| `RedisStreamClient` | type | The eight-method seam your app implements over its own Redis driver |
| `RedisChannelStore` | class (`ChannelStore`) | `new RedisChannelStore(client, { prefix? })` — the state of [text channels](/docs/agent/guides/channels) (message ids, questions, relayed outcomes) shared by every replica: `SET … PX … NX` claims, `GET`, `DEL`. Pass it as `AgentChannelsModule.forRoot({ store })` |
| `RedisChannelClient` | type | The three commands it uses (`set` with `PX`/`NX`, `get`, `del`) — an `ioredis` client has them as is |

## When to use it

Reach for this package the moment your app runs more than one replica behind a load balancer (or
serverless instances that don't share process memory) and you want `GET /agent/chat/:runId/stream`
to work no matter which instance handles the reconnect. Single-replica deployments — most local dev,
many small production deployments — are fine on the default `InProcessTokenStreamSink` and don't need
this package at all.

<Callout type="info" title="Several replicas, no Redis">
If you already run a SQL store, `DrizzleTokenStreamSink(db)` ([`-store-drizzle`](/docs/agent/packages/store-drizzle))
and `MikroOrmTokenStreamSink(em)` ([`-store-mikro-orm`](/docs/agent/packages/store-mikro-orm)) — both
built on core's `SqlTokenStreamSink` — keep frames in an `agent_stream_frame` table that every replica
polls. Coalesced text rows, a TTL (`ttlSeconds`, default 1h) with auto-purge, and polling latency
(`pollIntervalMs`, default 250ms) instead of pub/sub push.
</Callout>

<Callout type="warn" title="durable: true dispatches the turn's long steps">
Under `AgentModule.forRoot({ durable: true, ... })` the model call and each tool execution run as
routed durable steps, so they can execute on a *different* worker process than the one that opened
the stream — this is true even in a "single replica" web app paired with a separate durable worker
pool, not just multi-pod fleets. A cross-process sink like `RedisTokenStreamSink` is required
whenever the process that streams a chunk may differ from the one a client reconnects through; a boot
warning fires when durable is on with the default in-process sink.
</Callout>
